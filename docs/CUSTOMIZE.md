# 改造指南：让它评你们团队的规则

这个项目的代码是通用的，**规则是你的**。改规则不需要动架构，只需要动三个地方。

---

## 1. 改"必查清单"——改 prompt

位置：`src/reviewer.py` 里的 `_LOCAL_ITEMS` 和 `_GLOBAL_ITEMS`。

分批通道和全局通道的清单**必须不重叠**。开了全局通道时，分批通道的 prompt 里要显式声明"这四类由另一条通道负责，不要报"，否则同一问题报两遍。

改完之后：

```bash
python -m src.cli once --mr <编号> --dry-run
```

看输出的评论内容，判断是不是变成了你想要的样子。

---

## 2. 改"什么东西算横切文件"——改正则

位置：`.env` 的 `CROSS_PATTERNS`。

默认值是：

```
(?i)(filter|interceptor|security|auth|transaction|config|common|aspect)
```

这个正则是按 Spring 项目的结构写的。**换成别的技术栈必须改**，否则全局通道会"找不到任何横切文件"，越权/事务类问题全部漏掉。

排查方法：日志里出现 `全局检查：没找到任何横切文件` 就是这个问题。

调法：先手动列出你们项目里"鉴权在哪、事务配置在哪、公共上下文在哪"，然后照着文件/类名写正则。

---

## 3. 改群通知的粒度和路由——改策略

位置：`src/notify.py` 的 `notify_review()` 参数。

常见调整：

| 想要 | 怎么做 |
|---|---|
| 只推高危，低危不推群 | `level_filter={"high"}` |
| 每个仓库推不同的群 | 在调用处按 `mr["repo"]` 选 webhook 列表 |
| 不要 @所有人，只 @作者 | 在 `build_text` 里拼 attention 字段 |
| 消息里带 MR 标题和链接 | 已经带了，别删（末尾链接被截断是坑 8） |

---

## 4. 加一条新的"必查项"，完整流程

假设你要加"新增的定时任务必须有分布式锁"：

1. **写进规则清单**：`examples/review-rules.md` 的"必须报"里加一条
2. **写进 prompt**：`_LOCAL_ITEMS` 加 `7. 定时任务缺少分布式锁（多实例会重复执行）`
3. **造一个反例**：在测试仓库提一个真的没有锁的定时任务 MR
4. **dry-run 验证**：确认它能报出来，且**没有顺带报一堆无关问题**
5. **加进 eval 表**：`examples/review-rules.md` 第五节加一行
6. **观察一周**：如果出现误报，回到第 2 步收窄措辞

**第 4 步的"没有顺带报一堆无关问题"和第 6 步，是绝大多数人跳过的两步，也是效果差的根本原因。**

## 5. 换成私有部署的模型

如果公司不允许代码出内网，把模型换成本地推理服务：

```bash
LLM_BASE_URL=http://qwen-inference.default.svc:8000/v1
LLM_MODEL=qwen2.5-coder-32b
LLM_API_KEY=EMPTY
```

只要接口是 OpenAI 兼容的（`/v1/chat/completions`），代码不用改。

**代价（要提前知道）**：
- 效果会掉一档，尤其是跨文件的推理
- `response_format: json_object` 不少自建服务不支持，代码里已做降级重试
- 32B 以下的模型建议不要开全局通道，它处理长横切文件的能力不够
- 需要自己维护推理服务的显存和并发

---

## 6. 加"分支评审"（还没开 MR 就评）

当前版本只处理合并请求。如果想在分支推上来时就评，需要补三块：

1. **push 事件解析**：`refs/heads/<branch>` → 分支名，`after` → 新 HEAD
2. **diff 用分支 vs 基线**：`develop...feature/x`，**不要用 `before..after`**（那样只看本次推送，会漏掉分支上累积的问题）
3. **落点用提交评论**：`POST .../commits/{sha}/comments`，注意**不能行内**，也没有 List 接口读回校验

必要的闸门（任一命中就放弃，别浪费钱）：
- 是保护分支（master/main/develop）→ 不评
- 该分支已有 opened MR → 交给 MR 通道评，避免同一份代码评两遍
- 这个 sha 已经评过 → 跳过
- 提交信息含 `[skip-review]` / 纯格式化 / 纯文档 → 跳过
- 同一分支 60 秒内连续 push → 只评最后一个

---

## 一句话

**架构不用改，规则要一直改。** 这个工具的价值 20% 在代码，80% 在你持续往规则清单和 eval 表里加东西。

加不动了，它就退化成"一个会说话的 lint"；一直在加，它才会变成"一个知道你团队在意什么的人"。
