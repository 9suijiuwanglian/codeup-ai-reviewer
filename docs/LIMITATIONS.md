# 已知不足与限制

这份文档存在的目的，是让你在**上线前**就知道它会怎么让你失望，而不是上线后发现。

分四类：

- **A. 架构性缺陷** —— 改不掉，是这个方案的固有代价。只能接受，或者换方案。
- **B. 工程短板** —— 能改，但当前版本确实没有。你可以自己补。
- **C. 成本与风险** —— 上线前必须算的账。
- **D. 不该用的场景** —— 有些需求它天生满足不了，硬用只会更糟。

---

## A. 架构性缺陷（绕不过去）

### A1. 跨文件的判断天生不可靠

**现象**：改了 `order-service` 的接口，但鉴权规则在 `gateway` 的 filter 里。它很可能说"没有权限校验问题"，因为那个文件不在 diff 里。

**原因**：分批是按文件切的。模型看一批的时候，天然看不到别的文件。这不是模型能力问题，是**输入里根本没有那份信息**。

**缓解**：全局通道会额外读"横切文件"的全文（鉴权、拦截器、事务配置），能覆盖一部分。但它靠正则猜哪些文件算横切文件，猜错了就漏。

**结论：这一条只能减轻，不能消除。** 任何声称"AI 评审能完全替代人工 review"的方案，都在骗你。

---

### A2. 它不是确定性检查，同一份代码两次结论可能不同

**现象**：同一个 MR，今天跑说"1 个高危"，明天重跑说"2 个中危"。

**原因**：模型是概率性的。温度调低能减少抖动，但不能归零。

**后果（重要）**：**它不能作为合入门禁的唯一依据。** 也不能用来做"必须通过才能合并"的硬卡点——否则会出现"代码没改，昨天能过今天过不了"的荒唐情况。

**正确的用法**：它是 lint / SAST / 单元测试的**补充**，不是替代。确定性的检查交给确定性工具。

---

### A3. 误报的代价高于漏报

**现象**：它报了一条其实没问题的地方，开发去反驳，来回一轮。

**原因**：模型对"什么算问题"的标准，和你团队的标准不完全一致。尤其是风格类、设计取舍类的问题。

**后果**：**团队会因为噪音而关掉它。** 这是这类工具最常见的死法——不是不好用，是太吵。

**缓解**：靠规则清单（见 `examples/review-rules.md`）把"不该说的话"明确列出来。但这份清单只能靠你一条条攒，没有别的办法。

**这条没有技术解，只有运营解。**

---

### A4. 一次评审要 7~8 分钟，期间完全静默

**现象**：MR 提交后，评论和群消息都不来。等 8 分钟才出现。

**原因**：分批是**串行**的，每批约 110 秒。4 批就是 7 分多钟。而且这期间不发任何中间状态。

**后果**：用户会以为它挂了，反复提交、反复来问。**这是最高频的误判。**

**能不能改**：能，但成本高。批次之间其实可以并发（它们互不依赖），但会撞模型的速率限制，而且并发 4 批的费用和串行一样。当前版本为了稳，选择了串行。

**已经缓解了一半**：收到 push 时会先回写一个 `pending` 的提交状态，云效「自动化检查」里能看到它在跑。但这只解决"有没有触发"，解决不了"跑到第几批了"——中途失败还是只能看日志。占位评论这个方案没做，因为评论发出去就不能原地更新，追加一条反而更乱。

---

### A5. 对 Java / Spring 生态过拟合

**现象**：拿去评 Go 或前端项目，全局通道基本不工作。

**原因**：`CROSS_PATTERNS` 的默认正则（filter / interceptor / security / transaction / aspect）、必查清单（越权、事务边界、接口契约、并发），都是按 Spring 的实际结构写的。

**能不能改**：能，改配置和 prompt 就行。但**换生态等于重写一遍规则**，不是改个参数的事。

## B. 工程短板（当前版本确实没有）

| 短板 | 影响 | 你想补的话 |
|---|---|---|
| **没有验收集（eval）** | **这是最大的短板。** 我们不知道它的误报率、漏报率是多少。只知道"能发现真问题"，但说不清"多久误报一次" | 攒 30~50 个历史 MR + 人工标注，做成固定回归集。参考 `docs/CUSTOMIZE.md` |
| **没有数据库** | 状态存在 `state.json` 文件里，PVC 一丢就全丢 | 丢了会重评所有 opened MR，群里刷屏。最小改动：换 ConfigMap/外部 Redis |
| **单副本 / 无高可用** | 副本数必须 1，因为 RWO 云盘不能跨节点共享 state.json | 多副本会重复点评。可用 cronjob 兜底，但根治要换掉文件状态 |
| **没有分布式锁** | 双副本同时收到事件时靠 state 去重，有极小的竞态窗口 | 影响很小，但存在 |
| **只处理 opened 的 MR** | 已合并/关闭的 MR 补评不了 | 云效 API 只查 opened。要补评得自己存 MR 列表 |
| **提交评论不能行内** | 分支评审只能整条评论，问题靠"文件:行号"文字标注 | 云效 API 限制，提交评论没有 file_path 概念。行内只有 MR 有 |
| **没有"已收到"的中间反馈** | 见 A4，用户以为挂了 | 先发占位评论，评审完成后编辑/追加 |
| **没有 Web UI / 没有历史看板** | 想看"这个月评了多少 MR、发现多少问题"得自己拉日志 | 日志是 JSON 行，容易解析 |
| **没有 dry-run 的可视化对比** | 改了规则只能看 diff 文本 | — |

## C. 成本与风险（上线前必须算）

### C1. 钱

按实测：一个 61 文件的大 MR，4 批，每批输入约 10 万字符（≈2.3 万 token），输出 1~3 万 token。

粗算单次成本（以常见国产模型价格区间计）：**几毛到几块钱一个 MR**。

一天 50 个 MR，一个月就是几百到几千块。**这笔钱会出现在财务账上，提前和老板说好。**

省钱的有效手段（按效果排）：
1. 忽略无关文件（`IGNORE_PATH_PATTERNS`，把锁文件、静态资源排掉）
2. 过滤无意义提交（`[skip-review]`、纯格式化、纯文档）
3. 同一分支 60 秒内连续 push 只评最后一个
4. 关掉全局通道（省约 30%，但越权/事务类问题就没了）

### C2. 代码出公司

**这是很多公司根本不能用的原因，也是硬约束。**

评审意味着把你的源码发给第三方模型 API。无论对方承诺什么，对你公司来说这都是一次数据出境/出组织。

**必须先确认**：
- 公司安全策略允许吗？（金融、政企通常不允许）
- 用的是公有云 API 还是私有部署？
- 合同里有没有"不用于训练"的条款？

**缓解**：换私有部署的开源模型（Qwen / DeepSeek 等自托管），代价是效果下降一档，且要自己维护推理服务。

另外配置里 `CROSS_EXTS` **故意只读源码、不读 yml/properties**——因为配置文件里常有数据库口令和第三方密钥。这个默认值不要随手放开。

### C3. 依赖云效的非公开行为

payload 的字段（`relatedMergeItemType`、`patchSetName`、`project_id` vs `repositoryId`）很多是**实测出来的**，官方文档写得含糊或者根本没写。

**后果**：云效升级可能悄悄改字段，然后你就开始漏评——而且是静默的，不会报错。

**缓解**：定期跑 `check` 命令，比对 `state.json` 里最新版本和实际 MR 版本是否一致。

## D. 不该用的场景

| 场景 | 为什么不适合 | 该用什么 |
|---|---|---|
| 当作合入门禁（必须通过才能合） | 见 A2：非确定性，会说变就变 | lint / SAST / 单测 |
| 替代人工 code review | 见 A1：看不到全貌 | 人 |
| 团队还没有 review 文化 | 它评论没人看，很快就被静音 | 先建立人工 review 习惯 |
| 代码不允许出公司 | 见 C2 | 私有部署模型，或干脆不用 |
| MR 频率极高（一天几百个） | 单次几分钟 + 成本线性增长 | 只对关键分支/关键目录开启 |
| 想让它"教新人怎么写代码" | 它会给出听起来对但不可执行的建议 | 人带人 |

---

## 一句话总结

**它是一把"帮你多看一眼"的辅助工具，不是一把"替你签字"的刀。**

用得好，它能替你挡住那些"改完就忘、上线才想起"的低级错误；
用不好，它会变成一个刷满噪音、被全公司静音的群机器人。

差别不在代码，在你有没有把"什么算真问题"这条线划清楚。
