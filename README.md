# codeup-ai-reviewer

给阿里云云效 Codeup 用的 AI 代码评审机器人：MR 一提交，自动按你定的规则评审，评论写回云效，结论推到企业微信群。

市面上的 AI 评审方案几乎都是 GitHub / GitLab 的。云效 Codeup 用的人很多，但公开的自建方案基本没有。这个仓库把这套东西完整摊开——**六个关键设计、18 个坑，包括几个"不报错但结果是错的"的坑**。

东西是运维写的，不是做 AI 的。代码不漂亮，但线上跑了几个月。

---

## 核心方案

这六个设计，前三个决定它能不能用，后三个决定它会不会被关掉。里面对应的问题，基本是这类工具的通病。

### 一、两条通道，必查清单不重叠

**问题**：靠 diff 判断不了越权、事务边界、接口契约——这些信息不在改动的几行里，在另一个文件里。

**做法**：拆成两条通道。

| 通道 | 输入 | 查什么 |
|---|---|---|
| 分批通道 | 按文件切开的 diff | 空指针、注入、资源泄露、异常吞掉、边界 |
| 全局通道 | 鉴权、拦截器、事务注解等横切文件的**全文** | 越权、事务、接口契约、并发 |

关键在"不重叠"：开了全局通道后，分批通道的 prompt 里要把那四类**显式删掉**，并告诉模型"这四类由另一条通道负责，不要报"。否则同一个问题被报两遍，评审立刻变噪音。

```python
# src/reviewer.py: system_prompt()
def system_prompt(cfg):
    if cfg.global_review:
        # 全局通道开着：分批通道只拿本地清单，四类全局项一个字都不提
        return SYSTEM_PROMPT_LOCAL % _LOCAL_ITEMS
    # 全局通道关着：清单合并，所有项都由分批通道查
    return SYSTEM_PROMPT_FULL % (_LOCAL_ITEMS + "\n" + _GLOBAL_ITEMS)
```

不是"告诉它别报"，是**从模板里直接删掉**——模型看不到的东西，它不会想报。

### 二、版本去重：取 MERGE_SOURCE，不是列表最后一项

**问题**：这是最容易埋下的静默错误。云效 `/diffs/patches` 返回的列表里，最后一项是 **Base**（`relatedMergeItemType = MERGE_TARGET`），不是最新版本。Base 在目标分支不动时恒定不变——于是从第二个版本开始，每次推送都被判定为"已评审过"，直接跳过。

评的是旧代码，但评论照发、通知照推，**看起来一切正常**。

**做法**：过滤掉 MERGE_TARGET，按 `versionNo` 升序，取最后一个。

```python
# src/codeup.py: latest_patchset()
items = []
for p in as_list(data):
    kind = str(p.get("relatedMergeItemType") or "").upper()
    if kind and kind != "MERGE_SOURCE":
        continue                       # 跳过 Base / MERGE_TARGET
    vno = int(p.get("versionNo") or 0)
    items.append((vno, p.get("patchSetBizId") or ""))

items.sort(key=lambda x: x[0])
return items[-1][1]                    # 最新版本的 bizId
```

### 三、三层长度闸门

这类工具会撞三次长度墙，位置完全不同，要分开处理：

| 层 | 撞墙表现 | 处理 |
|---|---|---|
| 输入 | 上下文放不下 | 按文件切批，`maxDiffChars` 决定切几批 |
| 输出 | JSON 断在半路，整批白跑 | `max_tokens` 给足 + 尾部抢救 + 对半拆 |
| 评论 | 超过 65535 字符，**整条发不出去** | 按行切多条，`【AI 评审 i/n】` 标记，绝不丢内容 |

有一条反直觉，值得单独说：**调小 `maxDiffChars` 不会更安全**。它只会把文件切得更碎，让模型看到半个文件，误判率反而上升。实测 240 万字符的输入（约 59 万 tokens）照样能过，输入侧几乎没有约束。这个参数决定的是"分几批"，不是"能看多少"。

### 四、分级 + 条数上限：四十条等于零条

一个 MR 刷四十条评论，开发第二天就不看了。所以输出的**筛选比生成更重要**：

- 按严重度分级，只有高风险的推群，低风险的只落在 MR 评论里
- 单次最多推 `max_issues` 条（默认 5），其余写"另有 N 条低风险"
- 宁可漏，不可错——**误报一次，这个功能就被关了，而且不会给你第二次机会**

### 五、push 事件兜底对账

**问题**：云效的 push 事件 payload **只带 ref 和 repository，没有 MR 编号**。所以"从事件里直接拿到 MR"这条路不存在。

**做法**：扫这个仓库所有 opened MR，谁的版本变了就评谁（靠本地 state 去重）。

```
push 事件
└─ opened_mrs(only_repo=repo)
   └─ 版本变了的，评它
```

顺带一个必须做的事：**云效 webhook 配置里一定要勾上 push 事件**。只勾"合并请求"事件的话，MR 建好之后的提交会全部漏评，而且照样能合并。

### 六、上下文缺口声明

**问题**：分批之后，模型不知道自己只看到了一部分。它会很肯定地说"没有权限问题"——因为那份鉴权代码根本没在输入里。

**做法**：prompt 里明确告诉它缺了什么。

```
本批只包含以下 N 个文件：xxx
未包含：yyy
跨文件才能判定的问题，写成「需结合上下文确认」，并指明要核对哪个文件。
```

实测效果：加上这段之后，模型会主动说"鉴权情况需结合上下文确认"，而不是硬下结论。**这一条的收益比换模型大得多，成本为零。**

## 这些设计是怎么被逼出来的

前面每一条，背后都有一个坑。

### 它评了整整一周的旧代码

评论正常发出，群里通知也正常，内容却是上一版的。当时以为是模型问题，换模型、调 prompt、加重试，全没用。真正原因就是上面第二条——去重取了 Base。

更麻烦的是，云效合并时用的是**源分支当前内容**。所以那段时间"AI 说没问题"和"真正合进去的代码"，完全是两回事。

### helm upgrade 成功、Pod 重启了、参数一个没变

改 `LLM_MAX_TOKENS`，`helm upgrade` 报成功，`kubectl get pod` 是新 Pod，进去 `echo $LLM_MAX_TOKENS` — 还是旧值。

原因：chart 里设了 `existingSecret` 就不渲染 `secret.yaml`，而调参项恰好只写在那里面。改 `values.yaml` 等于没改。**每一步看起来都对，就是结果不对。**

这个 chart 现在所有调参项都用 `env` 显式下发。你新增任何一项都得照抄这个模式，否则同一个坑会再来一次。

### "没动静"其实是还在跑，我重启了三次

分批是**串行**的，4 批大约 7~8 分钟，期间完全静默——不发任何中间状态。

我看到群里没消息，以为挂了，`rollout restart`，重来一遍，等三分钟，再重启。

后来才想明白：**这类工具最该先做的不是"评得准"，是"让人知道它还在跑"。** 我们把它当黑盒，它就把我们当傻子。

## 快速开始（本地跑通，不碰集群）

```bash
git clone https://github.com/<YOUR_GITHUB>/codeup-ai-reviewer.git
cd codeup-ai-reviewer
pip install -r requirements.txt
cp .env.example .env          # 填 token / orgId / 仓库
python -m src.reviewer once --mr 1 --dry-run   # 只打印，不发评论
```

`--dry-run` 会把要发的评论正文打印到终端。确认没问题再去掉这个参数。

部署到 K8s / ACK 见 [docs/DEPLOY.md](docs/DEPLOY.md)。**装之前先读 [docs/PITFALLS.md](docs/PITFALLS.md)**，18 条，能省几个通宵。

## 先看缺点

**这个项目有明确的、改不掉的缺陷。装之前请先读完 [docs/LIMITATIONS.md](docs/LIMITATIONS.md)。** 摘要：

1. **跨文件的判断天生不可靠。** 分批后模型看不到全貌，改了接口而鉴权在别的模块这类问题会漏。全局通道只能补一部分。
2. **它不是确定性检查。** 同一份代码两次可能给出不同结论。**所以不能当合入门禁用**，也不能替代 lint / SAST / 单测——它是补充。
3. **误报的代价高于漏报。** 太吵的评审会被全公司静音。缓解只能靠你团队自己攒的"不该说什么"清单，没有技术解。
4. **一次评审 7~8 分钟，期间完全静默。** **别把"没动静"当成"失败了"**。
5. **单一语言过拟合。** 全局通道的规则是按 Spring 写的，换 Go / 前端等于重写规则。
6. **没有验收集。** 我们不知道它的误报率是多少——只知道它发现过真问题，没说清多久误报一次。这是当前最大的短板。
7. **状态存在文件里。** 没有数据库，PVC 丢 = 全丢，会重评所有 MR。副本限制为 1。
8. **代码会发给第三方模型。** 很多公司（金融、政企）因此根本不能用，这是硬约束，见 LIMITATIONS C2。

如果上面这几条里，有哪一条你接受不了——**那就不要用**。市面上没有能同时解决这些问题的方案，包括商业产品。
