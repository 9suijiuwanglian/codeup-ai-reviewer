# 评审规则清单（模板）

**这份文件比代码重要。**

AI 评审能不能用，不取决于模型多强，取决于你有没有把"什么算真问题"写清楚。
不写清楚，它就会按通用常识瞎猜，然后你会觉得"效果差"。

用法：复制这一份，按你们团队的情况填，然后（a）把"必须报"的部分贴进 `src/reviewer.py` 的
`_LOCAL_ITEMS`，（b）把"一律不提"的部分贴进 prompt 的禁止项，（c）拿它当评审标准去验收 AI 的输出。

---

## 一、必须报（会导致故障 / 数据错误 / 安全问题的）

按你们的技术栈填。下面是 Spring 微服务场景的参考，**留能用的，删不适用，加你们特有的**。

### 数据与事务
- [ ] 事务注解自调用失效（同类方法内部调用，事务不生效）
- [ ] 跨服务写操作没有补偿或幂等，重试会写双份
- [ ] 查询没走索引（大表 where 无索引字段、like 前置通配）
- [ ] 分页查询没有上限，可能全表捞出

### 安全与越权
- [ ] 新增接口的路径没有被鉴权拦截覆盖（尤其路径拼接、通配符、排除名单）
- [ ] SQL / 命令 / 路径拼接（没用参数化）
- [ ] 敏感信息进日志（token、口令、身份证、手机号）
- [ ] 硬编码密钥 / 测试后门接口
- [ ] 越权：只校验"已登录"没校验"是不是自己的数据"

### 稳定性
- [ ] 线程池 / 连接池未设上限，或在请求链路里创建
- [ ] 未兜底的远程调用（没超时、没降级、没重试上限）
- [ ] 循环里查数据库 / 调接口（N+1）
- [ ] 缓存没设过期时间，或缓存与库更新不同步
- [ ] 大对象 / 大集合一次性载入内存

### 并发与状态
- [ ] ThreadLocal 用完不清理（线程复用会导致身份串号）
- [ ] 单例里放可变成员变量
- [ ] 非原子操作计数（先用后加）

---

## 二、一律不提（报了就是噪音）

**这一栏比第一栏更能决定成败。** 一条噪音会让开发对整个机器人失去信任。

- [ ] 命名风格、变量长短
- [ ] 注释多少、有没有文档注释
- [ ] 代码格式、空行、import 顺序
- [ ] "建议加日志""建议加单元测试"这类**不可执行**的建议
- [ ] 已经存在的历史问题（不是这次改的）
- [ ] 纯重构类改动里的"改动太大，建议拆分"
- [ ] "这里可以更优雅""可以用设计模式"这类主观判断
- [ ] 跟业务无关的通用最佳实践（"建议使用构造器注入"）

---

## 三、有分歧时以谁为准

这一栏必须填，否则 AI 每次都会给你一个"两边都对"的答案。

| 场景 | 我们团队的做法 |
|---|---|
| 性能 vs 可读性 | 例：以可读性优先，除非在热点路径上 |
| 加抽象 vs 直接写 | 例：三处以上重复才抽象 |
| 异常吞掉 vs 抛出去 | 例：一律抛，由全局处理器统一处理 |
| 校验放 controller 还是 service | 例：入参格式在 controller，业务规则在 service |

---

## 四、判据：什么样的意见值得说

给每条 AI 意见过一遍这三问，任何一问过不去就删掉：

1. **能落到具体位置吗？** 说不出文件+行号的，不是问题，是感想。
2. **能说出后果吗？** "会导致并发下单重复扣款"能说清；"可能有问题"说不清。
3. **开发看了会改吗？** 如果他看完的反应是"哦，随便吧"，这条就不该发。

## 五、验收用的问题集（eval）

**这才是让这个工具变好的东西。** 攒 30~50 条，每次改 prompt 都跑一遍。

格式建议：

| # | MR 编号 | 期望它发现什么 | 期望它**不**说什么 | 上次结果 |
|---|---|---|---|---|
| 1 | !12 | 事务自调用失效 | 不提命名 | ✅ |
| 2 | !15 | 新接口未被鉴权覆盖 | 不提注释 | ❌ 漏了 |
| 3 | !18 | 无 | 无（干净代码，不许编问题） | ✅ |
| 4 | !21 | 分页没上限 | 不提索引 | ⚠️ 报了但定位错了 |

**第 3 行那种"干净的 MR 不许编问题"的用例最重要**——它测的是误报率，而误报才是杀死这个工具的真正原因。

每次改了 prompt 或换了模型，跑一遍这张表，记下通过率。没有这张表，你就是在凭感觉调，永远是"好像好了一点"。
